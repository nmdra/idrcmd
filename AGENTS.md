# AGENTS.md — idrcmd

> **Project:** `idrcmd` — **I Don't Remember Commands**  
> **Tagline:** *Remember the intent, not the command.*  
> **Purpose of this file:** Instructions for coding agents and contributors working in the `idrcmd` repository.  
> **Primary specification:** `./.agents/idrcmd-project-plan-turso.md`. When implementation details conflict, prefer the latest explicitly approved product decisions and update the plan alongside the code.

## 1. Mission and non-negotiable product behavior

Build an **offline-first, intent-driven Linux CLI** that lets users describe a daily task without recalling command names, flags, or syntax.

Example target UX (illustrative, not a claim that this is implemented):

```console
$ idrcmd convert photo.png to webp
✓ Created photo.webp

$ idrcmd make my video easier to share
? Which video file?
> holiday.mp4
Will create holiday_compressed.mp4. Proceed? [y/N] y
✓ Created holiday_compressed.mp4
```

The user expresses **what** they want. `idrcmd` chooses an **already registered and trusted capability**, grounds its arguments, asks for missing information, and runs it safely. **Do not** turn the product into an unrestricted AI shell or require the user to learn a new DSL.

Guiding principles:

1. **Intent over command syntax.** Natural-language requests are the primary interface.
2. **Minimal command registration.** For common tasks, a description and an argument-vector template are enough; richer hints must remain optional.
3. **Semantic retrieval first.** Use local embeddings and Turso vector similarity to shortlist tools. Do not require hand-written keywords or aliases.
4. **Needle proposes; Go decides.** AI output never grants authority to execute arbitrary commands.
5. **Offline by default.** Inference, retrieval, registry access, and core execution work without network access after setup. Some explicitly registered tools may use the network; disclose that to the user.
6. **Extensibility without retraining.** Adding/editing a tool updates the local registry and semantic index; never require fine-tuning for routine additions.
7. **Predictability and safety before autonomy.** A clear clarification or refusal is preferable to an ungrounded action.

## 2. Current technology decisions

- **Application:** Go, targeting Linux `amd64` and `arm64` initially.
- **Model:** Original Cactus **Needle 3 base** model; **no fine-tuning in MVP**.
- **Inference integration:** Native C API from Go via **cgo**; pin model weights, header, and library to mutually compatible versions.
- **Persistent local database:** **Embedded Turso Database**, through `turso.tech/database/tursogo` with Go `database/sql`.
- **Semantic retrieval:** Needle embeddings initially; native Turso vector functions (`vector32`, `vector_distance_cos`) with a top-K shortlist.
- **Execution:** Go `exec.CommandContext` with a trusted executable and **separate argv tokens**; no shell command generated by the model.
- **Cloud services:** None required for MVP. Do not silently use Turso Cloud, telemetry, network APIs, remote model inference, or synchronization.

**Version/API warning:** Do not assume older `cactus-needle`, newer `cactus-compute`, `libcactus`, and `libneedle` APIs are interchangeable. Inspect and pin the actual `needle.h`/C ABI and deployed `.cact` weights before writing or updating bindings. Likewise, **Turso Database is not the same as libSQL**; verify features against the chosen `tursogo` version rather than mixing documentation or assuming ANN indexes.

## 3. Responsibilities and trust boundaries

| Layer | Responsible for | Must NOT do |
|---|---|---|
| **Needle 3** | Generate query/tool embeddings (experimental); select a shortlisted tool; extract user-supported arguments; interpret follow-up text; optionally propose multiple calls | Execute shell commands, invent filesystem facts, grant permission, decide safety policy, invent missing values |
| **Turso** | Store command definitions, trust state, embeddings, index metadata, migrations, optional redacted history; perform local vector-distance queries | Independently authorize command execution |
| **Go** | CLI, command registry, schema compilation, retrieval orchestration, validation, clarification, filesystem checks, risk/approval policy, process execution, results | Treat model text or retrieval scores as verified facts or authority |
| **Registered tools** | Perform narrowly described, user-approved OS operations | Run if disabled, untrusted, malformed, or outside allowed risk policy |

Treat **user text, model output, tool metadata imported from other people, filenames, filesystem content, and command output as untrusted inputs**.

## 4. MVP boundaries

**Include:**

- Natural-language single-request CLI and `--dry-run` / `--explain`.
- Minimal command registry with `tools add`, `list`, `show`, `disable`, and `reindex`.
- Embedded Turso storage, migrations, local vector similarity, and top-K candidate retrieval.
- Base Needle tool selection and parameter extraction.
- One pending clarification flow, with deterministic Go prompts if information is missing.
- Safe single-command execution with timeouts, output bounds, explicit risk controls.
- A curated starter pack: image-to-WebP, video compression, audio extraction, archive creation, large-file search, service/process/port inspection, Git status, and Docker logs (stage rollout gradually).
- Offline smoke tests and benchmark fixtures for retrieval, routing, and safety.

**Exclude until explicitly scoped:**

- Model fine-tuning, arbitrary text-to-shell generation, autonomous privilege escalation, unreviewed destructive actions, cloud sync, general chatbot functionality, GUI, and voice control.
- General multi-step agent planning. Multiple Needle tool calls may be observed, but execution of chains requires an explicit, tested Go dependency/approval mechanism.

### Essential Go interfaces

Keep the model and storage implementations replaceable. Names below are illustrative; prioritize a clean contract over exact spelling.

```go
type Embedder interface {
    Embed(ctx context.Context, text string) ([]float32, error)
    ModelID() string
}

type CommandRepository interface {
    Add(ctx context.Context, command Command, embedding []float32) error
    Search(ctx context.Context, query []float32, modelID, indexVersion string, limit int) ([]Candidate, error)
    Get(ctx context.Context, id string) (Command, error)
}

type IntentEngine interface {
    Select(ctx context.Context, request string, candidates []Command) (Selection, error)
}
```

Use interfaces at **external boundaries** (model, database, command runner), not an abstraction for every small helper.

## 6. Tool definitions: minimal but safe

Example format (an **idrcmd convention**, not native Needle syntax):

```yaml
name: image_to_webp
description: Convert an image to WebP
command:
  - ffmpeg
  - -nostdin
  - -n
  - -i
  - "{input:file}"
  - -frames:v
  - "1"
  - -c:v
  - libwebp
  - "{output:.webp}"
```

Rules:

- Compile registration into a fixed **executable + argv template**. Never save a raw, dynamically interpolated shell string as the execution primitive.
- Infer placeholder names from the template. `:file` and `:.webp` are app-level conventions; implement them explicitly and document their meaning.
- Keep a short description required for semantic indexing. Detailed per-argument questions, aliases, examples, and types are **optional hints**, not mandatory configuration.
- Derive output filenames through **well-defined Go rules**; the model must not fabricate input paths or overwrite targets.
- Validate imported definitions and require **explicit trust/approval** before they become executable. Tool definitions may be malicious.
- Preserve command arguments as tokens; never concatenate user text into shell syntax.
- Reject unknown placeholders, malformed templates, and placeholders that can replace the executable or inject unapproved flags.
- Treat output path conflicts as blocking unless the policy explicitly requests and authorizes overwrite.

## 7. Semantic registry and Turso

### Storage requirements

Use XDG-compatible paths, with overrides:

```text
$XDG_CONFIG_HOME/idrcmd/config.toml
$XDG_DATA_HOME/idrcmd/idrcmd.db
$XDG_CACHE_HOME/idrcmd/models/needle3.cact
```

Fall back to `~/.config`, `~/.local/share`, and `~/.cache` when relevant XDG variables are absent. Create required parent directories and apply reasonable local file permissions. Never require a Turso Cloud account for local execution.

Persist at least:

- Command ID, name, description, executable/argv, risk, enabled and trusted flags, creation/update times, and content hash.
- Embedding records with command ID, **model ID**, vector dimension, preprocessing/index version, and content hash.
- Schema migrations and an atomic indication of the **active** semantic index.
- Optional, bounded, **redacted** execution history (no raw secrets or sensitive arguments by default).

### Retrieval path

1. Embed the user intent locally.
2. Ensure query embedding model ID/dimension match the active index.
3. Search **only enabled, trusted commands** using Turso cosine distance; start with top **5** candidates.
4. Fetch selected command definitions and compile their Needle function schemas.
5. Use Needle to choose a proposed tool and extract arguments; do not execute merely because a vector is nearest.
6. If retrieval is weak or ambiguous, ask the user to clarify or show choices. **Cosine similarity is not a confidence probability.**

Use bound SQL parameters; never concatenate user-provided values into SQL. `vector32()` and `vector_distance_cos()` must be verified with the **pinned** Turso driver through an actual local integration test.

### Embedding preprocessing

- Start with **raw cosine** as the baseline.
- Experiment with **mean-centered and re-normalized** vectors, but do **not** assume it improves a real command catalog: the example notebook's result is a tiny sample.
- If centering is enabled, store the centroid and index version; apply the same transform to queries and stored commands. Rebuild/swap indexes atomically when the command set changes.
- Needle's supplied embeddings are **experimental for semantic search**. Keep `Embedder` replaceable with a dedicated local model if Recall@5 falls short.
- Do not compare vectors from different model builds or preprocessing versions.

## 8. Needle inference behavior

- Use the **base model**, not an assumed fine-tuned checkpoint.
- Generate Needle tool schemas from **shortlisted** registry entries, not the entire catalog.
- Keep parameters optional in the **model-facing** schema when necessary to learn intent with incomplete user requests; Go still enforces required template values.
- Treat an **empty/suppressed call** as ambiguous: it might mean unsupported intent, insufficient context, or missing required information.
- Never guess absent filenames, directories, container names, destructive targets, or numeric settings. Defaults must be explicitly defined and deterministic.
- Interpret follow-up text only within the active pending action; clear context between unrelated CLI invocations to avoid stale tool calls.
- Serialize native inference unless the pinned C library explicitly guarantees concurrency safety. Manage C memory ownership and model lifecycle carefully; add lifecycle/error tests.
- Tool-call confidences, if available, are diagnostic signals **only**—not permissions, calibrated probabilities, or safety guarantees.

## 9. Clarification and action lifecycle

Model the action lifecycle explicitly:

```text
REQUESTED → RETRIEVED → SELECTED → NEEDS_INPUT → VALIDATED
                                              ↘ CANCELLED
VALIDATED → PREVIEW/APPROVAL → EXECUTING → COMPLETED | FAILED
```

- At most **one pending action** in the initial MVP.
- If an input is missing, derive a short question from the placeholder name and optional description, e.g. “Which video file should I use?” No pre-authored question is required.
- If the user says “latest MP4 in Downloads”, resolve it with deterministic filesystem logic and confirm if more than one reasonable file matches.
- Accept explicit cancellation and do not execute after cancellation.
- Revalidate all resolved paths, overwrites, privileges, and other preconditions **immediately before execution**.
- Display the resolved action on `--dry-run` and `--explain` without running the tool.
- For any ambiguous request, favor clarification over best-guess execution.

## 10. Execution and safety policy — mandatory

**Never use `sh -c`, `bash -c`, `eval`, or model-written shell scripts to carry out a user request.** Use only approved registered executables and separate validated argv tokens through `exec.CommandContext`.

Risk policy:

| Tier | Typical examples | Allowed behavior |
|---|---|---|
| 0 — Read-only | Git status, inspect port, list files | May run when grounded and trusted |
| 1 — Create output | Convert image, generate archive | Non-overwriting, validated destination; preview when unclear |
| 2 — Modify existing state | Rename, move, overwrite | Require explicit preview and confirmation |
| 3 — Privileged/destructive | Delete data, change services, install packages | **Out of scope for MVP** |

Mandatory protections:

- Validate executable registration/trust **and** all model-proposed argument names/values.
- Use explicit path validation, symlink-aware checks where appropriate, constrained file scopes for dangerous operations, and `--` delimiters or equivalent protection against filenames interpreted as flags.
- Set command timeouts and bound stdout/stderr capture; support cancellation and preserve meaningful exit errors.
- Don't silently overwrite, delete, escalate privileges, make network requests, or execute imported templates.
- Reject direct invocation of unregistered executables, user-supplied pipes, command substitutions, shell redirects, and model-generated flags outside the template.
- Do not feed command output directly back as executable instructions; it is data.
- Never add logging that exposes tokens, credentials, private paths, or file contents without explicit user control.
- **Never weaken these guarantees to make an end-to-end demo pass.**

## 11. Engineering workflow for agents

When implementing a task:

1. **Read `AGENTS.md` and the current project plan first.** Identify the affected subsystem and scope.
2. Inspect the repository's actual Go module, package structure, migrations, and native artifacts before writing code. **Do not assume prototypes or previous zip releases are present.**
3. For Cactus or Turso API work, consult the **version-pinned** headers/docs and existing tests. Verify names/signatures rather than guessing.
4. Make the **smallest coherent change** with explicit interfaces at I/O boundaries and direct error propagation.
5. Add or update tests for normal, missing, malformed, ambiguous, unsupported, and unsafe inputs.
6. Run the relevant tests and checks. Distinguish **mock/stub tests** from **real native integration tests**.
7. Update README, example tool packs, migrations, and project plan when behavior or architecture changes.
8. In your final implementation report, state: files changed, observed tests/results, unverified assumptions, safety considerations, and next milestone.

Do not say “works end-to-end” if only a C stub or fake embedder was used. If native assets are unavailable, test the Go layers using fakes, mark real integration **unverified**, and retain an executable smoke-test path for the target Linux machine.

### Coding conventions

- Prefer idiomatic Go, small packages, context propagation, table-driven tests, and explicit returned errors.
- Avoid package-global mutable state except the narrowly scoped native inference lifecycle when required by the actual C API.
- Keep parsing, schema validation, retrieval, risk policy, and execution separately testable.
- Wrap optional cgo dependencies behind build tags or thin adapters **if needed** so pure-Go tests can run without native artifacts. Never present a stub build as production inference.
- Avoid unnecessary network dependencies in normal operation.
- Pin module and native dependency versions; document checksums or provenance for downloaded model/runtime artifacts.
- Add migrations rather than silently mutating schema assumptions.

## 12. Test and evaluation requirements

Maintain fixtures for at least these cases:

1. **Correct direct action:** “convert `photo.png` to webp” picks the registered converter and extracts `photo.png`.
2. **Synonyms:** “make this picture a WebP” retrieves the converter without exact keywords.
3. **Missing input:** “compress a video” asks for a filename; **does not invent one**.
4. **No match:** “book me a flight” returns no actionable CLI tool if none exists.
5. **Ambiguous:** “do something with these files” does not trigger a guessed destructive operation.
6. **Untrusted tool:** Registered but untrusted commands cannot run.
7. **Unknown argument/flag:** Model-invented arguments are rejected.
8. **Destination exists:** Conversion never overwrites without explicit approval.
9. **Injection attempts:** Paths containing quotes, spaces, `;`, `$()`, or leading `-` cannot escape argv validation.
10. **Cancellation/timeout:** Pending or running operations terminate appropriately.
11. **Stale vector index:** Changed command descriptions or model IDs force reindexing or a clear error.
12. **Offline operation:** Normal retrieval, routing, and execution do not depend on an active network.

Suggested evaluation targets (**not measured model claims**):

| Metric | MVP target |
|---|---:|
| Semantic Recall@5 on held-out requests | ≥ 95% |
| Final tool selection on supported, unambiguous requests | ≥ 90% |
| Correct extraction of explicitly supplied arguments | ≥ 90% |
| Missing-input clarification | ≥ 95% |
| Unsupported/no-match rejection | ≥ 95% |
| Unapproved destructive/untrusted execution | **0 observed** |

Evaluate raw and mean-centered embeddings on the **same** held-out dataset. Include realistic paraphrases, similar commands, invalid values, and negative/unsafe requests. Report retrieval metrics separately from Needle tool-selection metrics. A finite safety suite cannot prove the absence of all vulnerabilities.

### Commands to run where supported

```bash
go fmt ./...
go vet ./...
go test ./...
go test -race ./...         # When native build/runtime permits it
```

Also maintain a **real-native smoke test** that loads the pinned `.cact` model, generates one embedding, retrieves a command from local Turso, obtains one model tool-call proposal, and validates a read-only action. Do not execute risky actions as part of CI.

## 13. Milestone order and completion gates

- **M0 — Native feasibility:** real Go/cgo Needle inference + embedding; real local Turso insert/query/vector-distance; verified offline and persistent across restarts. **No stub-only signoff.**
- **M1 — Semantic command registry:** command CRUD/trust, minimal template compiler, embeddings, raw-cosine search, indexing/reindexing, top-K retrieval, migration tests.
- **M2 — Intent-driven execution:** model shortlist selection, grounded parameters, missing-value clarification, safe `exec.CommandContext`, dry-run and explanations. Validate three complete scenarios.
- **M3 — Useful tool packs and hardening:** ~10 curated daily actions, risk controls, no-overwrite behavior, executable presence checks, optional redacted history, negative/safety testing.
- **M4 — Beta:** benchmarking, Linux amd64/arm64, backup/restore, packaging, documentation, offline install/use verification.

**Do not skip M0** or make claims of a native integration based on a mock build. Keep M1/M2 changes narrow and observable so failures can be attributed to retrieval, model selection, argument handling, or execution.

## 14. Definition of done for any feature

A feature is done only if:

- It directly helps the user complete an intent without memorizing command syntax.
- It preserves the **trusted registry → semantic retrieval → Needle proposal → Go validation → execution** boundary.
- It works without cloud dependencies in the documented local mode.
- It has tests for expected behavior and relevant negative/security cases.
- Its CLI UX does not demand unnecessary tool configuration.
- Documentation and migrations reflect its actual behavior.
- Verified outcomes are distinguished from examples and assumptions.
